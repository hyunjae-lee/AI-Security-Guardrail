# 전교 도입 설계 — 규모·구조·비용

> 이 문서의 수치는 **실측**과 **가정**을 구분해 적는다.
> 실측 = 이 저장소의 도구로 잰 값. 가정 = 모르는 값이라고 밝히고 범위로 둔 것.
> 2026-10-04 기준.

## 0. 한 줄 결론

**검사 엔진은 병목이 아니다.** 구성원 14,000명 전원이 적극적으로 써도 코어 2개면
처리된다(실측 기반). 돈과 시간이 드는 곳은 서버가 아니라 **① 트래픽을 어떻게
게이트웨이로 모으느냐 ② 등급표를 누가 쓰느냐 ③ 운영 인력** 셋이다.

## 1. 가장 어려운 문제 — 트래픽을 어떻게 모으나

「네트워크에서 생성형 AI 트래픽을 필터한다」는 말에는 **검사**와 **강제** 두 가지가
섞여 있다. 검사는 이미 만들었다. 강제는 아직 없고, 선택지마다 비용과 법적 부담이
다르다.

| 방식 | 어떻게 | 강제력 | 복호화 | 비용 | 판단 |
|---|---|---|---|---|---|
| **A. 유인** | 교내 AI 포털·게이트웨이를 더 편하게 만들어 자발적으로 쓰게 | 없음 | 불필요 | 최저 | **1단계** |
| **B. 직접 접속 차단** | 캠퍼스 egress 에서 외부 AI API 도메인을 SNI/DNS 로 차단, 게이트웨이만 허용 | 중 | **불필요** | 낮음 (기존 장비 설정) | **2단계** |
| **C. TLS 인터셉션** | 전 구성원 단말에 기관 CA 를 깔고 HTTPS 를 복호화 | 높음 | 필요 | 높음 + 법무 | **권장하지 않음** |

**C 를 권장하지 않는 이유**는 비용이 아니라 성격이다. 구성원 통신을 기관이 복호화하는
것은 통신비밀 문제이고, BYOD 가 많은 대학에서 전 단말 CA 배포는 현실성이 낮으며,
인증서 피닝을 쓰는 앱은 그냥 깨진다. 얻는 것에 비해 치르는 것이 너무 크다.

### 그래서 무엇을 막는 시스템인가 — 솔직하게

A+B 로는 **악의적 우회를 막지 못한다.** 개인 핫스팟을 켜면 그만이다.
이 시스템이 막는 것은 **사고**다 — 붙여넣기, 공유 버튼, 첨부파일. 삼성도 구글 색인도
EchoLeak 도 전부 평범한 업무 동작에서 났다. Okta 조사에서 로그인 정보까지 넣은 16% 는
숨기려던 사람이 아니라 **그게 위험한 줄 몰랐던 사람**이다.

**전면 금지가 답이 아닌 이유도 같다.** 삼성은 금지했고, 업무는 그대로 남았고, 도구만
보이지 않는 곳으로 옮겨 갔다. 유인(A)이 금지보다 강한 통제인 경우가 많다.

### 1-A. 채널별로 — 무엇이 막히고 무엇이 안 막히나

「포털을 운영한다」는 말이 의미를 가지려면 **다른 길이 닫혀 있어야 한다.**
그런데 길마다 닫히는 정도가 다르다. 전부 같은 도메인을 쓰기 때문에
**교내망 안에서는 네 가지가 한 번에 막힌다.**

| 채널 | 무엇을 쓰나 | 교내망에서 차단되나 | 방법 |
|---|---|---|---|
| 웹 브라우저 | chatgpt.com · claude.ai · gemini.google.com | ✅ | SNI/DNS |
| **데스크톱 앱** | 같은 도메인 | ✅ | 같음 |
| **모바일 앱 (교내 Wi-Fi)** | 같은 도메인 | ✅ | 같음 |
| **API 연동** (연구실 코드) | api.openai.com · api.anthropic.com | ✅ | 같음 |
| **모바일 데이터(LTE/5G)** | 같은 도메인 | ❌ **막을 수 없다** | — |
| 개인 핫스팟·테더링 | 같은 도메인 | ❌ | — |
| VPN | 터널 안이라 안 보인다 | △ 군비경쟁 | 알려진 VPN 엔드포인트 차단 |
| **업무도구 내장 AI** | Office Copilot · Workspace Gemini ·<br>GitHub Copilot · Notion AI | △ **정책 결정 필요** | 막으면 생산성 도구가 함께 죽는다 |

복호화는 필요 없다. **끊는 것**이지 들여다보는 것이 아니기 때문이다
(인증서 피닝도 차단에는 걸림돌이 아니다 — 연결을 떨어뜨릴 뿐이다).

### 1-B. 닫히지 않는 구멍 — 주머니 속의 폰

**교내 Wi-Fi 를 끄고 LTE 로 붙으면 그만이다.** 이건 네트워크 정책으로 못 막는다.
단말 관리(MDM)로 가려면 BYOD 인 대학에서 개인 폰을 기관이 관리한다는 뜻이고,
그건 할 수도 없고 해서도 안 된다.

그래서 이 시스템의 위협 모델을 분명히 해야 한다.

| 막는 것 | 못 막는 것 |
|---|---|
| **사고** — 편하니까 붙여넣는다 | **고의 우회** — 막힌 걸 알고 폰을 꺼낸다 |
| 삼성 붙여넣기 · 구글 색인 · Okta 의 16% | 작정하고 빼내려는 내부자 |
| 게이트웨이·포털이 다룬다 | 인사·징계·접근통제가 다룬다 |

실제 사고는 거의 전부 왼쪽이다. 오른쪽은 **보안 게이트웨이의 문제가 아니라
조직의 문제**이고, 그렇게 말하는 편이 정직하다.

### 1-C. 순서 — 차단이 먼저가 아니다

> **포털을 먼저 열고, 그다음 차단한다.**

반대로 하면 삼성이 된다. 금지했지만 업무는 그대로 남았고 도구만 보이지 않는 곳으로
옮겨 갔다. 그 순간 가시성은 **부분에서 0 으로** 떨어진다 — 차단 전에는 적어도
누가 무엇을 쓰는지 봤는데, 차단 후에는 폰으로 넘어가 아무것도 안 보인다.

**차단의 효과는 대안의 품질에 비례한다.** 대안이 나쁘면 차단은 가시성을 없애는
장치가 되고, 대안이 좋으면 차단은 거의 필요 없어진다.

### 1-D. 포털이 이기는 이유 — 금지가 아니라 경쟁력

구성원이 포털을 **고르게** 만드는 것들. 위에서부터 효과가 크다.

| 무엇 | 왜 외부 서비스가 못 따라오나 |
|---|---|
| **교내 자료 연동 (RAG)** | 「우리 학과 졸업요건은?」 「연구비 정산 서류는?」 에<br>ChatGPT 는 **구조적으로** 답할 수 없다. 자료가 없다.<br>이 저장소의 `rag.py` 가 CLR 등급으로 걸러 답한다 |
| **기관이 비용 부담** | 개인 돈으로 월 2~3만 원 내던 것을 안 내도 된다 |
| 더 나은 모델 | 개인은 무료 티어, 포털은 유료 API |
| 교내 SSO | 계정을 따로 만들지 않는다 |
| 한도·속도 | 무료 티어의 사용량 제한이 없다 |

**RAG 가 결정적이다.** 나머지는 외부 서비스가 가격을 내리면 따라올 수 있지만,
교내 규정·매뉴얼·학사 자료는 그쪽에 없다. 포털만 할 수 있는 일을 주는 것이
차단보다 강한 통제다.

### 1-E. 되고 있는지 어떻게 아나 — 측정 가능하다

우회 여부는 추측할 필요가 없다. **포털 트래픽을 기대 수요와 비교하면 된다.**

- 구성원 14,000명 · 채택률 가정 85% → 중간 시나리오로 하루 약 178,500건
- 포털 실제 처리량이 그 10분의 1이라면, 나머지는 **다른 길로 가고 있다는 뜻**이다

`GET /api/ops` 가 내는 일일 처리량이 이 지표다. 파일럿에서 이 숫자를 보고
차단 범위를 조절한다 — 숫자 없이 「다 막았으니 됐다」고 말하지 않는다.

### 1-F. 앱·CLI·IDE 는 어떻게 하나 — 세 갈래로 갈린다

브라우저가 아닌 경로가 실제로는 더 많다. 그런데 셋이 성격이 완전히 다르다.

| 갈래 | 무엇 | 끝단을 바꿀 수 있나 | 방법 |
|---|---|---|---|
| **A. 개발 도구** | Claude Code · Codex · OpenAI SDK ·<br>Cursor · Continue · LangChain | ✅ **된다** | 게이트웨이로 돌린다 — 이미 되는 길 |
| **B. 소비자 앱** | ChatGPT · Claude 데스크톱/모바일 앱 | ❌ 안 된다 | 차단 + **포털로 대체** |
| **C. 끼워진 AI** | Office Copilot · Workspace Gemini ·<br>GitHub Copilot | ❌ 안 된다 | **정책 결정** — 테넌트 설정으로 경계 제한 |

#### A — 개발 도구: 환경변수 하나다

```bash
# Claude Code (서버·개인 PC 공통)
export ANTHROPIC_BASE_URL=https://ai.kaist.ac.kr
export ANTHROPIC_AUTH_TOKEN=<교내 발급 토큰>    # API_KEY 가 아니라 AUTH_TOKEN 이다

# OpenAI SDK · Codex 계열
export OPENAI_BASE_URL=https://ai.kaist.ac.kr/v1
export OPENAI_API_KEY=<교내 발급 토큰>
```

Claude Code 는 `~/.claude/settings.json` 의 `env` 블록으로도 고정할 수 있어
**서버 이미지나 dotfiles 에 심어 두면 사용자는 평소처럼 `claude` 만 치면 된다.**

게이트웨이 쪽은 LiteLLM 이 **Anthropic 형식 `/v1/messages`** 와 OpenAI 형식
`/v1/chat/completions` 를 모두 낸다. Claude Code 를 받으려면 `/v1/messages` 와
`/v1/messages/count_tokens` 를 서비스하고 `anthropic-version`·`anthropic-beta`
헤더를 그대로 넘겨야 한다.

**강제 방법은 둘을 겹친다.** 환경변수를 기본값으로 배포하고(편의), 외부 AI
도메인을 차단한다(강제). 둘 중 하나만으로는 샌다.

#### B — 소비자 앱: 여기가 포털이 존재하는 이유

ChatGPT·Claude 데스크톱 앱에는 **커스텀 엔드포인트 설정이 없다.** 바꿀 수단이
아예 없으므로 차단하고 포털로 옮기는 것 말고 방법이 없다. 다행히 이 앱을 쓰는
사람들은 코드를 쓰지 않으므로 **포털 웹 화면으로 충분하다.**

#### C — 끼워진 AI: 기술이 아니라 정책

Copilot 류는 끝단도 경로도 우리 것이 아니다. 막으면 생산성 도구가 함께 죽는다.
현실적인 선택은 **기업 테넌트 설정으로 데이터 경계를 제한**하는 것이고,
그 결정은 기술이 아니라 기관의 판단이다. 이 문서는 답을 정하지 않는다.

### 1-G. 코딩 도구가 가장 위험한 경로다

Claude Code·Codex 는 **소스코드를 읽어서 보낸다.** 레포 전체, 설정 파일,
`.env` 까지 올라간다. 채팅 프롬프트와는 노출 규모가 다르다.

측정해 보면 **엔진이 거기서 가장 잘 동작한다.**

| 페이로드 | 글자수 | 검사 시간 | 처리량 |
|---|---|---|---|
| 채팅 질의 | 26 | 3.3 ms | 307 req/s |
| 코드 파일 1개 + `.env` | 12,122 | **9.6 ms** | 105 req/s |
| 레포 맥락 (3배) | 36,366 | **28.0 ms** | 36 req/s |

> 한국어 2,000자가 98 ms 인데 코드 12,000자가 9.6 ms 인 것은 **언어 라우팅**
> 덕분이다. 코드는 한글 비율이 낮아 한국어 NER 경로를 타지 않는다
> (`_languages_for`). 영어 경로는 규칙만 돌아서 훨씬 싸다.

그리고 실제로 잡는다 — 위 코드 페이로드에서 `secret.openai_key`,
`secret.db_uri`, `anomaly.high_entropy` 가 걸려 **100점 BLOCK** 이 났다.
`.env` 가 섞여 나가는 것이 코딩 도구의 가장 흔한 사고인데, 그게 정확히 걸린다.

### 1-H. 알려진 위험 — 스트리밍 응답 시작까지의 지연

출력 검사가 **꼬리를 붙잡기** 때문에(`inspect_output_stream`) 첫 글자가 나오기까지
약간 늦어진다. LiteLLM 의 Anthropic 패스스루에도 큰 프롬프트에서 TTFT 가 길어져
클라이언트가 무응답으로 보고 끊는 보고가 있다(BerriAI/litellm #32491).

**코딩 도구는 프롬프트가 크므로 이 위험이 가장 크다.** 완화책 셋:
1. `hold` 를 줄인다 — 다만 짧을수록 경계에 걸친 패턴을 놓칠 여지가 는다
2. 입력 검사 결과가 깨끗한 요청은 출력 쪽 `hold` 를 낮춘다 (위험도 기반)
3. 클라이언트 타임아웃을 넉넉히 잡도록 안내한다

파일럿에서 **실제 TTFT 를 재서** 정한다. 지금은 측정값이 없다.

## 2. 규모 산정

### 2.1 실측 — 이 저장소의 엔진 성능

`scripts/eval.py` · `web/tools/bench-latency.py` 로 잰 값. Apple M1 Pro, 단일 프로세스,
balanced 프로파일, 한국어 NER(ONNX) 포함.

| 워크로드 | 처리량 | 1건당 |
|---|---|---|
| 짧은 질의만 (100자) | 318 req/s | 3.1 ms |
| **현실 혼합** (짧음 90% · 중간 9% · 긴 글 1%) | **115 req/s** | 8.7 ms |
| 문서 붙여넣기 많음 (70 / 25 / 5) | 46 req/s | 21.9 ms |

메모리는 워커당 **약 1 GB** (ONNX Runtime + 토크나이저 포함. 규칙만이면 27 MB).

### 2.2 가정 — 수요

실측할 수 없는 값이라 **가정임을 밝히고 범위로 둔다.**

- 구성원 **13,986명** (재학생 12,348 + 교직원 1,638, 2025 기준) → 14,000 으로 계산
- 채택률 **85%** 가정 (국내 일반 74%, 과학기술원이므로 상향) → 활성 11,900명
- 피크 시간에 하루 물량의 **15%** 가 몰리고, 피크 초는 그 시간 평균의 **3배** 가정

| 시나리오 | 1인 1일 질의 | 하루 질의 | 피크 평균 | **피크 순간** |
|---|---|---|---|---|
| 보수 | 5 | 59,500 | 2.5 req/s | **7.4 req/s** |
| 중간 | 15 | 178,500 | 7.4 req/s | **22.3 req/s** |
| 적극 | 40 | 476,000 | 19.8 req/s | **59.5 req/s** |

### 2.3 필요한 서버

서버 CPU 는 M1 Pro 보다 코어당 느리므로 **0.6 배**로 할인하면 프로세스당 약 **69 req/s**
(현실 혼합 기준).

| 시나리오 | 피크 | 필요 프로세스 | 권장 (3배 여유 + HA) |
|---|---|---|---|
| 보수 | 7.4 | 0.1 | 2노드 × 2워커 |
| 중간 | 22.3 | 0.3 | 2노드 × 2워커 |
| **적극** | **59.5** | **0.9** | **2노드 × 4워커** |

**적극 시나리오에서도 프로세스 하나로 처리된다.** 2노드로 가는 이유는 성능이 아니라
가용성이다 — 한 대가 죽어도 질의가 검사 없이 나가면 안 된다.

> **다만 긴 문서가 변수다.** 10,000자 붙여넣기는 질의 검사에 488 ms 가 든다(실측).
> 문서 붙여넣기 비중이 25% 를 넘으면 처리량이 46 req/s 로 떨어지므로, 그때는
> 워커를 늘리거나 긴 입력에 별도 큐를 둔다.

## 3. 시스템 구조

```
  [구성원 단말]
       │ ① 교내 SSO 로 인증 (CLR 등급이 여기서 나온다)
       ▼
  ┌─────────────────────────────────────────┐
  │  교내 AI 포털 (웹 UI)  │  OpenAI 호환 API │   ← 사람용 / 앱·연구실용
  └─────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────┐
  │  LiteLLM 프록시  (2노드, LB 뒤)            │
  │    └ 커스텀 가드레일 ──HTTP──┐             │
  └─────────────────────────────┼───────────┘
                                ▼
                     ┌────────────────────┐
                     │ 가드레일 게이트웨이  │  ← 이 저장소
                     │  출국 검사 · 입국 검사│
                     └────────┬───────────┘
                              │ 판정만 기록 (원문 미저장)
                              ▼
                     ┌────────────────────┐
                     │ 감사 DB (PostgreSQL)│
                     └────────────────────┘
       │
       ▼  ② 캠퍼스 egress — 외부 AI 직접 접속은 차단, 이 경로만 허용
  [외부 생성형 AI]
```

**왜 LiteLLM 과 가드레일을 HTTP 로 나누나** — LiteLLM 이 최신 pydantic 을 요구해서
이 저장소의 `pydantic==2.10.4` 와 충돌한다(확인함). 나눠 두면 의존성이 독립하고,
가드레일을 고쳐도 프록시를 다시 배포할 필요가 없다.

**게이트웨이가 죽으면 차단이 기본값이다.** 검사 없이 국경을 넘는 것이 이 프로젝트가
막으려는 바로 그 상황이라, 조용히 통과시키는 쪽을 기본으로 둘 수 없다.

## 5-A. 교내 서버로 구축한다면 — 실제 사양

### GPU 는 필요 없다

먼저 이것부터 못박는다. 이 시스템은 **GPU 가 필요 없다.**
한국어 NER 은 KoELECTRA-small 을 ONNX 로 구워 **CPU 에서 3 ms** 에 돈다(실측).
「AI 시스템이니 GPU 서버가 필요하다」는 가정이 견적을 10배로 부풀리는 가장 흔한 원인이다.

### 자원별 산정 근거

| 자원 | 실측/계산 | 적극 시나리오 요구 | 권장 |
|---|---|---|---|
| **CPU** | 현실 혼합 115 req/s / 프로세스 (M1 Pro)<br>서버 코어 0.6배 할인 → 69 req/s | 피크 59.5 req/s → **프로세스 1개** | 노드당 **8코어**<br>(워커 4 + 프록시 + 여유) |
| **메모리** | 워커당 **1.0 GB** (ONNX+토크나이저 포함) | 워커 4 + 프록시 2 GB + OS 2 GB ≈ 8 GB | 노드당 **64 GB**<br>(페이지 캐시·여유) |
| **디스크** | 감사 레코드 **434 bytes/건** | 75 GB/년 → 3년 보존 225 GB | **NVMe 960 GB ×2 (RAID1)** |
| **네트워크** | 질의 2 KB + 응답 4 KB 가정 | 59.5 req/s × 6 KB ≈ **2.9 Mbps** | **1 GbE 로 충분** |
| **GPU** | — | **불필요** | — |

> CPU 권장이 요구(1 프로세스)보다 8배 큰 이유는 성능이 아니라 **운영 여유**다.
> 한 노드가 빠져도 남은 노드가 전체를 받아야 하고, 문서 붙여넣기가 몰리면
> 처리량이 46 req/s 로 떨어지며, OS·로그·백업이 코어를 쓴다.

### 감사 로그 보존

| 시나리오 | 하루 | 1년 | 3년 |
|---|---|---|---|
| 보수 (5질의/일) | 26 MB | 9.4 GB | 28 GB |
| 중간 (15질의/일) | 78 MB | 28.3 GB | 85 GB |
| 적극 (40질의/일) | 207 MB | 75.4 GB | **226 GB** |

**원문을 저장하지 않기 때문에** 레코드가 434 bytes 로 작다.
원문 앞 280자를 함께 담으면 레코드가 3~4배가 되고, 그만큼 **유출 시 피해도 커진다.**

### 구성 제안

| 단계 | 구성 | 사양 | 비고 |
|---|---|---|---|
| **파일럿** | 기존 가상화에 VM 1대 | 4 vCPU / 16 GB / 200 GB | 1개 부서 100~300명. 추가 하드웨어 0 |
| **전교 (가상화)** | 기존 가상화에 VM 2대 + DB VM 1대 | 8 vCPU / 32 GB / 500 GB ×2<br>4 vCPU / 16 GB / 500 GB ×1 | **추가 하드웨어 비용 없음 — 권장** |
| **전교 (전용 서버)** | 1U 서버 2대 | 1소켓 8~16코어 / 64 GB /<br>NVMe 960 GB ×2 (RAID1) / 듀얼 1GbE | 아래 가격 |

### 전용 서버를 새로 산다면

1소켓 1U 보급형(Dell PowerEdge R360, HPE ProLiant DL320 Gen11 급)이 정확히 이 체급이다.
국내 기준 R360 베이스가 420만 원(세전)이고, 16코어·64 GB·NVMe RAID1 로 올리면
**대당 700만~900만 원** 선이다.

| 항목 | 수량 | 금액 |
|---|---|---|

| 랙·전원·네트워크 포트 | — | 기존 전산실 활용 시 0 |
| **초기 합계** | | **1,400만~1,800만 원** |

**클라우드(월 56만 원)와 비교하면 2~3년이면 역전된다.** 다만 교내 가상화에 얹을 수

### 이 사양으로 어디까지 버티나

| | 적극 시나리오 피크 | 권장 구성 능력 | 여유 |
|---|---|---|---|
| 짧은 질의 중심 | 59.5 req/s | 노드당 4워커 × 69 = 276 req/s<br>2노드 = 552 (1노드 장애 시 276) | **4.6배** |
| 문서 붙여넣기 25% | 59.5 req/s | 노드당 4 × 28 = 112 (1노드 시) | 1.9배 |

**구성원 14,000명이 1인당 하루 40질의를 보내도 한 노드로 버틴다.**
여유가 가장 적은 경우(문서 붙여넣기가 전체의 25%)에도 1.9배가 남는다.

### 5.3 LLM API — 여기가 진짜 돈이다

중간 시나리오(월 535만 건), 질의 평균 800 토큰 · 응답 400 토큰 가정:

| 모델 | 월 비용(개산) |
|---|---|
| 저가형 (GPT-4o-mini 급, $0.15/$0.60 per 1M) | 약 **280만 원** |
| 고성능 (Claude Sonnet 급, $3/$15 per 1M) | 약 **6,500만 원** |

**가드레일 인프라는 AI 예산의 1% 미만이다.** 이 비교가 중요하다 — 검사 비용을 아끼려고
검사를 안 하는 것은 경제적으로도 말이 안 된다.
