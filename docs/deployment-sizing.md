# 전교 도입 설계 — 규모·구조·비용

> 이 문서의 수치는 **실측**과 **가정**을 구분해 적는다.
> 실측 = 이 저장소의 도구로 잰 값. 가정 = 모르는 값이라고 밝히고 범위로 둔 것.
> 2026-10-04 기준.

## 0. 한 줄 결론

**검사 엔진은 병목이 아니다.** 구성원 14,000명 전원이 적극적으로 써도 코어 2개면
처리된다(실측 기반). 돈과 시간이 드는 곳은 서버가 아니라 **① 트래픽을 어떻게
게이트웨이로 모으느냐 ② 등급표를 누가 쓰느냐 ③ 운영 인력** 셋이다.

---

## 1. 가장 어려운 문제 — 트래픽을 어떻게 모으나

「네트워크에서 생성형 AI 트래픽을 필터한다」는 말에는 **검사**와 **강제** 두 가지가
섞여 있다. 검사는 이미 만들었다. 강제는 아직 없고, 선택지마다 비용과 법적 부담이
다르다.

| 방식 | 어떻게 | 강제력 | 복호화 | 비용 | 판단 |
|---|---|---|---|---|---|
| **A. 유인** | 교내 AI 포털·게이트웨이를 더 편하게 만들어 자발적으로 쓰게 | 없음 | 불필요 | 최저 | **1단계** |
| **B. 직접 접속 차단** | 캠퍼스 egress 에서 외부 AI API 도메인을 SNI/DNS 로 차단, 게이트웨이만 허용 | 중 | **불필요** | 낮음 (기존 장비 설정) | **2단계** |
| **C. TLS 인터셉션** | 전 구성원 단말에 기관 CA 를 깔고 HTTPS 를 복호화 | 높음 | 필요 | 높음 + 법무 | **권장하지 않음** |

**C 를 권장하지 않는 이유**는 비용이 아니라 성격이다. 구성원 통신을 기관이 복호화하는
것은 통신비밀 문제이고, BYOD 가 많은 대학에서 전 단말 CA 배포는 현실성이 낮으며,
인증서 피닝을 쓰는 앱은 그냥 깨진다. 얻는 것에 비해 치르는 것이 너무 크다.

### 그래서 무엇을 막는 시스템인가 — 솔직하게

A+B 로는 **악의적 우회를 막지 못한다.** 개인 핫스팟을 켜면 그만이다.
이 시스템이 막는 것은 **사고**다 — 붙여넣기, 공유 버튼, 첨부파일. 삼성도 구글 색인도
EchoLeak 도 전부 평범한 업무 동작에서 났다. Okta 조사에서 로그인 정보까지 넣은 16% 는
숨기려던 사람이 아니라 **그게 위험한 줄 몰랐던 사람**이다.

**전면 금지가 답이 아닌 이유도 같다.** 삼성은 금지했고, 업무는 그대로 남았고, 도구만
보이지 않는 곳으로 옮겨 갔다. 유인(A)이 금지보다 강한 통제인 경우가 많다.

## 2. 규모 산정

### 2.1 실측 — 이 저장소의 엔진 성능

`scripts/eval.py` · `web/tools/bench-latency.py` 로 잰 값. Apple M1 Pro, 단일 프로세스,
balanced 프로파일, 한국어 NER(ONNX) 포함.

| 워크로드 | 처리량 | 1건당 |
|---|---|---|
| 짧은 질의만 (100자) | 318 req/s | 3.1 ms |
| **현실 혼합** (짧음 90% · 중간 9% · 긴 글 1%) | **115 req/s** | 8.7 ms |
| 문서 붙여넣기 많음 (70 / 25 / 5) | 46 req/s | 21.9 ms |

메모리는 워커당 **약 1 GB** (ONNX Runtime + 토크나이저 포함. 규칙만이면 27 MB).

### 2.2 가정 — 수요

실측할 수 없는 값이라 **가정임을 밝히고 범위로 둔다.**

- 구성원 **13,986명** (재학생 12,348 + 교직원 1,638, 2025 기준) → 14,000 으로 계산
- 채택률 **85%** 가정 (국내 일반 74%, 과학기술원이므로 상향) → 활성 11,900명
- 피크 시간에 하루 물량의 **15%** 가 몰리고, 피크 초는 그 시간 평균의 **3배** 가정

| 시나리오 | 1인 1일 질의 | 하루 질의 | 피크 평균 | **피크 순간** |
|---|---|---|---|---|
| 보수 | 5 | 59,500 | 2.5 req/s | **7.4 req/s** |
| 중간 | 15 | 178,500 | 7.4 req/s | **22.3 req/s** |
| 적극 | 40 | 476,000 | 19.8 req/s | **59.5 req/s** |

### 2.3 필요한 서버

서버 CPU 는 M1 Pro 보다 코어당 느리므로 **0.6 배**로 할인하면 프로세스당 약 **69 req/s**
(현실 혼합 기준).

| 시나리오 | 피크 | 필요 프로세스 | 권장 (3배 여유 + HA) |
|---|---|---|---|
| 보수 | 7.4 | 0.1 | 2노드 × 2워커 |
| 중간 | 22.3 | 0.3 | 2노드 × 2워커 |
| **적극** | **59.5** | **0.9** | **2노드 × 4워커** |

**적극 시나리오에서도 프로세스 하나로 처리된다.** 2노드로 가는 이유는 성능이 아니라
가용성이다 — 한 대가 죽어도 질의가 검사 없이 나가면 안 된다.

> **다만 긴 문서가 변수다.** 10,000자 붙여넣기는 질의 검사에 488 ms 가 든다(실측).
> 문서 붙여넣기 비중이 25% 를 넘으면 처리량이 46 req/s 로 떨어지므로, 그때는
> 워커를 늘리거나 긴 입력에 별도 큐를 둔다.

## 3. 시스템 구조

```
  [구성원 단말]
       │ ① 교내 SSO 로 인증 (CLR 등급이 여기서 나온다)
       ▼
  ┌─────────────────────────────────────────┐
  │  교내 AI 포털 (웹 UI)  │  OpenAI 호환 API │   ← 사람용 / 앱·연구실용
  └─────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────┐
  │  LiteLLM 프록시  (2노드, LB 뒤)            │
  │    └ 커스텀 가드레일 ──HTTP──┐             │
  └─────────────────────────────┼───────────┘
                                ▼
                     ┌────────────────────┐
                     │ 가드레일 게이트웨이  │  ← 이 저장소
                     │  출국 검사 · 입국 검사│
                     └────────┬───────────┘
                              │ 판정만 기록 (원문 미저장)
                              ▼
                     ┌────────────────────┐
                     │ 감사 DB (PostgreSQL)│
                     └────────────────────┘
       │
       ▼  ② 캠퍼스 egress — 외부 AI 직접 접속은 차단, 이 경로만 허용
  [외부 생성형 AI]
```

**왜 LiteLLM 과 가드레일을 HTTP 로 나누나** — LiteLLM 이 최신 pydantic 을 요구해서
이 저장소의 `pydantic==2.10.4` 와 충돌한다(확인함). 나눠 두면 의존성이 독립하고,
가드레일을 고쳐도 프록시를 다시 배포할 필요가 없다.

**게이트웨이가 죽으면 차단이 기본값이다.** 검사 없이 국경을 넘는 것이 이 프로젝트가
막으려는 바로 그 상황이라, 조용히 통과시키는 쪽을 기본으로 둘 수 없다.

## 4. 아직 없는 것 — 전교 운영에 필요한 개발

지금 있는 것은 **엔진과 데모**다. 운영하려면 다음이 더 필요하다.

| # | 무엇 | 왜 | 규모 |
|---|---|---|---|
| 1 | **KAIST SSO 연동** | CLR 등급을 실제 신원에서 가져와야 한다. 지금은 파라미터로 받는다 | 중 |
| 2 | **교내 AI 포털 (웹 UI)** | 일반 구성원이 쓸 화면. 이것이 없으면 「유인」 전략이 성립하지 않는다 | 대 |
| 3 | **감사 로그 운영화** | sqlite → PostgreSQL, 보존 기간 정책, 조회·통계 화면 | 중 |
| 4 | **등급표 관리 화면** | 각 부서가 직접 L0~L4 를 정의한다. 우리가 대신 쓸 수 없다 | 중 |
| 5 | **고가용성** | 2노드 + 로드밸런서 + 헬스체크. 지금은 단일 컨테이너 | 소 |
| 6 | **쿼터·레이트 리밋** | LLM 비용 통제. 이게 없으면 비용이 통제되지 않는다 | 소 |
| 7 | **모니터링·알림** | 판정 분포 급변, 게이트웨이 장애 | 소 |

**2번(포털)이 가장 크고 가장 중요하다.** 구성원이 쓸 이유가 없으면 강제도 의미가 없다.

## 5. 비용

### 5.1 인프라 — 생각보다 싸다

국내 클라우드 기준 (2026-02 조사: NCP 4vCPU/16GB/100GB SSD **월 181,740원**,
KT Cloud 월 223,550원).

| 항목 | 사양 | 월 비용 |
|---|---|---|
| 가드레일 + 프록시 | 4vCPU/16GB × 2 (HA) | 약 36만 원 |
| 감사 DB | 2vCPU/8GB + 100GB | 약 15만 원 |
| 로드밸런서 | — | 약 5만 원 |
| **합계 (클라우드)** | | **월 약 56만 원 / 연 670만 원** |

**교내 인프라를 쓰면 추가 하드웨어 비용은 사실상 0 이다.** 요구 사양이
가상머신 두 대 수준이라, KAIST 가 이미 운영하는 가상화 기반에 얹으면 된다.
온프렘 전용 서버를 새로 산다면 1U 서버 2대 약 1,500만 원(5년 상각 시 월 25만 원).

### 5.2 강제 계층

| 방식 | 비용 |
|---|---|
| SNI/DNS 기반 차단 (B) | **0 원** — 기존 방화벽 정책 변경 |
| TLS 인터셉션 (C) | NGFW 라이선스 수천만 원 + 단말 CA 배포 공수 + 법무 검토 |

### 5.3 LLM API — 여기가 진짜 돈이다

중간 시나리오(월 535만 건), 질의 평균 800 토큰 · 응답 400 토큰 가정:

| 모델 | 월 비용(개산) |
|---|---|
| 저가형 (GPT-4o-mini 급, $0.15/$0.60 per 1M) | 약 **280만 원** |
| 고성능 (Claude Sonnet 급, $3/$15 per 1M) | 약 **6,500만 원** |

**가드레일 인프라는 AI 예산의 1% 미만이다.** 이 비교가 중요하다 — 검사 비용을 아끼려고
검사를 안 하는 것은 경제적으로도 말이 안 된다.

### 5.4 운영 인력 — 가장 큰 비용

| 역할 | 공수 |
|---|---|
| 룰·코퍼스 유지, 오탐 대응 창구 | 0.5 FTE |
| 등급표 관리 지원 (각 부서와 협의) | 0.3 FTE |
| 인프라 운영 | 0.2 FTE |
| **합계** | **약 1 FTE** |

연 인건비 기준 **4,000만~8,000만 원**. 인프라(연 670만 원)의 6~12배다.

### 5.5 총계

|---|---|---|
| 인프라 | 670만 원 | 670만 원 |
| 개발 (4장의 7개 항목) | 0.5~1 인년 | — |
| 운영 | 1 FTE | 1 FTE |

## 6. 단계적 도입

| 단계 | 범위 | 하는 일 | 기간 |
|---|---|---|---|
| **1. 파일럿** | 1개 학과 또는 행정부서 (100~300명) | API 게이트웨이 + SSO. 실제 질의로 오탐률 재측정 | 2~3개월 |
| **2. 포털** | 희망 부서 확대 | 교내 AI 포털 공개, 쿼터·감사 운영화 | 3~4개월 |
| **3. 강제** | 전교 | 외부 AI API 직접 접속 차단, 게이트웨이 경유만 허용 | 2개월 |
| **4. 확대** | — | 교내 로컬 LLM(국내선) 연계, 에이전트 도구 호출 통제 | — |

**1단계에서 반드시 다시 재야 하는 것**: 지금의 오탐률 0%(하드)는 우리가 만든
코퍼스 205건 기준이다. 실제 부서의 질의 분포는 다르고, 거기서 오탐이 나오면
**업무가 멈춘다.** 파일럿의 목적은 기능 확인이 아니라 **그 부서의 정상 질의로
오탐률을 다시 재는 것**이다.

## 7. 이 분석의 한계

- **수요 가정**(1인 1일 질의 수, 채택률)은 실측이 아니다. 파일럿에서 실제 값을 잰다.
- 처리량은 **M1 Pro 단일 프로세스** 값에 0.6 배 할인을 적용한 추정이다.
  배포 호스트에서 `web/tools/bench-latency.py` 를 다시 돌려야 한다.
- LLM 비용은 모델·토큰 수 가정에 따라 20배 이상 벌어진다. 모델 선정이 정해지면 다시 계산한다.
- 클라우드 요금은 2026-02 조사값이고 공공기관 할인·계약 조건은 반영하지 않았다.
